# Сбор данных и модерация RustApp

## Что происходит после запуска

1. **Слушатель `listener` подключается к WebSocket RustApp.** После подписки он запрашивает первую страницу списка игроков проекта по HTTP, до 200 записей. Из неё берёт игроков со статусом `online` или `afk`, сохраняет известные типы клиентов и ставит этих игроков в очередь PostgreSQL `collection_jobs`. После переподключения без восстановления пропущенных событий слушатель загружает снимок заново.
2. **Обработчик `moderation` загружает историю банов и берёт игроков по одному.** При запуске он сначала сверяет баны с RustApp. Затем выбирает одну готовую задачу с самым ранним временем обработки. Для каждой пары «проект и SteamID» в очереди одна запись, поэтому повторный вход обновляет её.
3. **Новые входы идут в ту же очередь.** Пока обработчик разбирает стартовый список, слушатель уже принимает обновления по WebSocket. Переход из `joining` или `offline` в `online` или `afk` ставит игрока на сбор. WebSocket сообщает об изменении статуса. Профиль, точное время входа, тип клиента и боевую ленту обработчик получает отдельными HTTP-запросами к RustApp. Порядок задач определяется временем обработки, поэтому для входов нет отдельной очереди или отдельного прохода.
4. **Первый проход собирает данные.** Обработчик сохраняет профиль, историю сессий, статистику, жалобы, число проверок и первую страницу боевой ленты с логами попаданий. По истории сессий он определяет, может ли применить правила. Под блокировки попадают подтверждённые пиратские сессии на сервере наблюдения. Профили лицензионных игроков и игроков из белого списка тоже пополняют архив.
5. **Открытая сессия получает повторные проверки.** Через 45 секунд по умолчанию задача снова становится доступна в очереди. Для того же входа обработчик обновляет историю сессий и боевую ленту, а профиль берёт из базы. При закрытии сессии опрос прекращается. Если новый вход ещё не появился в истории RustApp, обработчик может повторять запрос до пяти минут после постановки задачи. Под нагрузкой фактический интервал зависит от длины очереди и пауз между запросами.
6. **Если правило сработало, приложение сохраняет основание.** Код паттерна, пороги и события попадают в `moderation_decisions`. При включённых автобанах после обработки игрока воркер пытается отправить одно решение из очереди блокировок. Перед отправкой он сверяет белый список, текущую сессию, её IP и действующие баны. Затем ищет созданный бан в панели RustApp и записывает подтверждение в базу и журнал.

Время первых минут игры берётся из истории RustApp. Стартовый список и время постановки задачи служат для планирования обработки.

## Запуск

Используются существующая PostgreSQL проекта и настроенные секреты панели и базы. Из корня репозитория:

```sh
docker compose --profile tools build listener moderation migrate
docker compose --profile tools run --rm migrate
docker compose --profile tools up -d listener moderation
```

По умолчанию система записывает правила и предполагаемые действия локально. Для отправки решений перед запуском задайте `APP_MODERATION_ENFORCE=true`. При смене настройки пересоздайте контейнер moderation. Каждый отправленный бан действует бессрочно на всех серверах проекта и блокирует SteamID и IP текущей игровой сессии. Если IP отсутствует или некорректен, обработчик помечает решение как `failed` и записывает причину в журнал. `APP_MODERATION_SERVER_ID` задаёт сервер наблюдения (по умолчанию №163).

## Какие данные собираются

- При входе: подробный профиль, сессии, статистика за 30 дней, первая страница полученных жалоб, общее количество проверок, первая страница боевой ленты вместе с логами попаданий. Изменившиеся ответы остаются в `rustapp_observations` с временем получения. Убийства с идентификаторами событий дополнительно попадают в `combat_kills`.
- В открытой сессии обработчик повторно запрашивает сессии и боевую ленту. По умолчанию обработанный игрок возвращается в очередь через 45 секунд, общий промежуток между запросами одного обработчика — 1 секунда. Настройки — `APP_MODERATION_POLL_SECONDS` и `APP_MODERATION_REQUEST_INTERVAL`. На загруженном сервере очередь увеличивает задержку. Если между опросами прошло больше 25 боевых событий игрока, на последней странице могут отсутствовать более ранние события.
- Баны проекта записываются в `rustapp_bans`. Первичная загрузка охватывает последнюю страницу (50 записей); глубина первого запуска на пустой таблице задаётся `APP_MODERATION_INITIAL_BAN_PAGES`. При последующих сверках обработчик доходит до известной записи или конца истории. Для правил связей используются активные записи с причиной «чит». Бан, вынесенный связкой P01/P02, исключён из исходных примеров. Бан по самостоятельному правилу может использоваться после подтверждения соответствующей записи панели. Перед отправкой по P02 или P04 проверяется, что исходный бан всё ещё действителен.

## Правила

Модули находятся в `app/services/moderation/patterns/`. P01 фиксирует совпадение регистрации Steam с ранее забаненным аккаунтом в пределах ±60 секунд. P02 может выдать бан при таком совпадении, если исходный бан предшествовал появлению новичка максимум на час. Для отправки по этой связке у обоих правил должно быть действие `ban`.

| Код | Независимое основание |
|---|---|
| P03 | Закрытый профиль без даты Steam и 3 разные жертвы за первые 10 минут первой игровой сессии новичка |
| P04 | Такой профиль и вход в течение 15 минут после бана другого пиратского аккаунта на сервере |
| P05 | 3 разные жертвы убиты в голову с 50 м за 30 минут |
| P06 | 3 разные жертвы убиты в голову за 30 минут, в логе каждой минимум 2 попадания стрелка с уроном по ней, все в голову |
| P07 | Минимум 5 убийств с 20 м за 30 минут, минимум 80% в голову |
| P09 | 3 разные жертвы за 30 минут в первый час после создания профиля на проекте |

Для P05–P07 учитываются винтовки, ПП и пулемёты по списку из исследования. Конфигурация правил передаётся JSON в `APP_MODERATION_PATTERNS`. Пример изменения двух правил:

```json
{"P05":{"meters":70,"version":2,"action":"ban"},"P04":{"action":"review"}}
```

Допустимые действия: `off`, `observe`, `review`, `ban`. Значения неуказанных порогов берутся из настроек соответствующего правила.

## Как разобрать бан

В комментарии RustApp сохраняются ID решения, код основного паттерна и краткое описание. Для просмотра полного основания решения №42:

```sh
docker compose --profile tools run --rm moderation python -m app.workers.show_decision 42
```

В `moderation_decisions` хранится одно решение на сессию. В нём видны версия и настройки каждого сработавшего паттерна, исходные ID банов или убийств, фактические показатели и время. Если одновременно подходят несколько оснований для бана, приоритет имеют P02, P06, P05, P03, P07, P04, P09 в указанном порядке. P01 отдельно сохраняет совпадение.

Журнал обработчика можно смотреть командой `docker compose logs -f moderation`. В режиме наблюдения строка содержит предлагаемую причину; при включённой отправке журнал показывает отправку, затем подтверждение панели с номером бана. В обеих строках видны SteamID, код правила и фактическое основание.

Состояние `recorded` означает локальную запись, `pending` — очередь на отправку, `sending` — отправка началась и ещё не подтверждена в списке банов. После обнаружения комментария с идентификатором решения сохраняются `confirmed` и ID бана RustApp. При потерянном ответе обработчик ищет этот комментарий. Если результат остаётся неизвестным, запись остаётся в `sending` для сверки модератором. Действующий бессрочный бан всего проекта с блокировкой того же IP даёт состояние `superseded`. Несовпадение параметров выданного бана при сверке или окончательный отказ панели дают `failed`, изменение условий перед отправкой — `cancelled`.
