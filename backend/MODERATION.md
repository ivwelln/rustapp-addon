# Сбор данных и модерация RustApp

## Веб-панель мониторинга

[Локальная панель](http://127.0.0.1:8000/) получает обновления от PostgreSQL по SSE. В списке видны игроки со статусами `online` и `afk`, имя, SteamID, белый список, провайдер, страна и убийства за 24 часа по собранным килллогам. Аккаунты из белого списка идут после остальных. В панели также доступны очередь проверок, журнал решений, аварийный лимит и график обращений к RustApp за час.

В таблице K/D показывает убийства и смерти за 24 часа по сохранённой боевой ленте. Красным вверху выделяются подтверждённые пиратские аккаунты вне белого списка, у которых больше пяти убийств и меньше двух смертей. Значок часов рядом со статусом показывает секунды с последней автоматической проверки. Эти данные приходят из PostgreSQL, а секунды обновляются в браузере.

## Что происходит после запуска

1. **Слушатель `listener` подписывается на WebSocket RustApp.** После подключения он получает общий список игроков по HTTP. Снимок даёт имена, сетевые сведения, сервер и тип клиента. Новые входы обновляют список сразу по WebSocket и запускают групповое чтение профилей с паузой минимум в минуту между снимками.
2. **Обработчик `moderation` загружает историю банов и берёт игроков по одному.** При запуске он сначала сверяет баны с RustApp. Затем выбирает одну готовую задачу с самым ранним временем обработки. Для каждой пары «проект и SteamID» в очереди одна запись, поэтому повторный вход обновляет её. Белый список проверяется при постановке в очередь и перед обработкой ранее поставленной задачи.
3. **Новые входы идут в ту же очередь.** WebSocket сообщает статусы входа, AFK и выхода. Сервис хранит текущий статус и подтверждённые интервалы нахождения на сервере. Если вход не был виден, поля, которые требуют его времени, остаются неизвестными.
4. **Первый проход собирает данные.** Обработчик сохраняет профиль, статистику, жалобы, число проверок и первую страницу боевой ленты с логами попаданий. Под блокировки попадают подтверждённые пиратские подключения на сервере наблюдения.
5. **Активный игрок получает повторные проверки.** Через 150 секунд задача снова становится доступна в очереди. Обычно повторная проверка запрашивает только боевую ленту. Если RustApp ещё не сообщил вход, задача может быть отложена. При AFK персональный опрос приостанавливается, а при выходе задача снимается с очереди. До подтверждения статуса `online` персональные запросы не отправляются.
6. **Если правило сработало, приложение сохраняет основание.** Код паттерна, пороги и события попадают в `moderation_decisions`. При включённых автобанах после обработки игрока воркер пытается отправить одно решение из очереди блокировок. Перед отправкой он сверяет белый список, текущую сессию, её IP и действующие баны. Затем ищет созданный бан в панели RustApp и записывает подтверждение в базу и журнал.

P03 использует время подтверждённого входа по WebSocket. P04 дополнительно требует события `joining`. HTTP-снимок даёт состояние «сейчас на сервере», без точной минуты начала игры.

Если снимок игроков завершился ошибкой, слушатель повторяет запрос с растущей паузой. При потере подтверждений WebSocket проверки игроков приостанавливаются через 60 секунд. Игровое время учитывается до последнего подтверждения связи.

## Запуск

Используются существующая PostgreSQL проекта и настроенные секреты панели и базы. Из корня репозитория:

```sh
docker compose --profile tools build api listener moderation ban-guard migrate
docker compose --profile tools run --rm migrate
docker compose --profile tools up -d --wait api listener moderation
```

По умолчанию система записывает правила и предполагаемые действия локально. Для отправки решений перед запуском задайте `APP_MODERATION_ENFORCE=true`. При смене настройки пересоздайте контейнер moderation. Каждый отправленный бан действует бессрочно на всех серверах проекта и блокирует SteamID и IP текущей игровой сессии. Если IP отсутствует или некорректен, обработчик помечает решение как `failed` и записывает причину в журнал. `APP_MODERATION_SERVER_ID` задаёт сервер наблюдения (по умолчанию №163).

## Диагностические логи

`docker compose logs -f listener moderation ban-guard` показывает обращения к RustApp, HTTP-статусы, время обработки игрока и решения о блокировке. Если нужно видеть очередь, работу кэша, проверку паттернов и длительность операций PostgreSQL, задайте `APP_LOG_LEVEL=DEBUG` в `.env` и пересоздайте контейнеры. Логи SQL содержат тип операции, длительность и число строк. HTTP-логи показывают метод и путь без параметров запроса и тела.

## Пауза в AFK

Пока последний известный статус игрока — `afk`, обработчик пропускает персональные запросы. При `afk → online` проверка становится доступной сразу. Для уже известной сессии время входа и имеющиеся данные сохраняются. При старте и переподключении без восстановления пропущенных событий актуальный снимок RustApp обновляет статусы. Сверка банов на уровне проекта продолжается.

## Белый список

Достаточно подтверждённой лицензии или **более 3 часов** игры на сервере наблюдения за последние 365 дней. Время складывается из ранее сохранённых завершённых сессий и собственных интервалов с подтверждённым сервером. Новые данные `session-history` сервис не запрашивает и не сохраняет. Периоды, когда подключение или сервер не удалось подтвердить, не засчитываются.

При входе или проверке очереди белый список читается локально из PostgreSQL. Добавление сохраняется в `players.is_whitelisted` и больше не пересчитывается. Причина автоматического добавления записывается в `players.whitelist_reason` как `license` или `playtime`. После добавления индивидуальные запросы по игроку прекращаются. Общие запросы списка игроков и банов проекта продолжат возвращать записи о таких аккаунтах.

## Какие данные собираются

- `rustapp_player_data` хранит одну строку на аккаунт проекта. В `responses` записываются последние ответы по каждому разделу и время их получения. Изменения ответов дополнительно сохраняются в `rustapp_observations`. Миграция переносит уже собранные данные из этого архива.
- Сохраняются подробный профиль, статистика за 30 дней, общее число проверок, полученные жалобы, IP и боевая лента. В `combat_kills` записываются PvP-убийства с исходными данными и логом попаданий. В `rustapp_player_ips` адреса хранятся с первым и последним наблюдением, в `rustapp_player_reports` жалобы сохраняются по ID. Отдельные истории команды и ников не запрашиваются.
- Профиль, статистика, число проверок и история IP обновляются при новом входе, если данным уже 10 минут. Полученные жалобы при активной сессии можно обновлять раз в 10 минут. В обычном цикле для игрока вне белого списка запрашивается боевая лента. Повторная обработка планируется через 150 секунд, между запросами обработчика выдерживается пауза 1 секунда. Настройки — `APP_MODERATION_POLL_SECONDS` и `APP_MODERATION_REQUEST_INTERVAL`. Для убийств, жалоб и истории IP берётся первая страница. В боевой ленте до 25 событий, включая смерти.
- Баны проекта записываются в `rustapp_bans`. Общая сверка `/ban/browse` проходит при запуске и каждые 5 минут. Глубина первичной загрузки задаётся через `APP_MODERATION_INITIAL_BAN_PAGES`, по умолчанию загружаются последние 50 записей. Сверка отправленных решений проходит раз в минуту и начинает с локальной базы. Для недавно отправленного бана может потребоваться одна досрочная общая сверка, если игрок уже вышел или ушёл в AFK. Для P01, P02 и P04 используются действующие баны с причиной «чит». Баны по связке P01/P02 исключены из исходных примеров. Перед отправкой сервис проверяет действующий бан игрока и заново проверяет исходный бан для P02 и P04.

## Аварийный лимит и счётчик RustApp

Внутренний сервис `ban-guard` разрешает приложению выдать максимум три автобана на проект. Разрешение записывается в PostgreSQL до отправки бана. Ранее выданные приложением баны засчитываются, включая те, у которых при сверке обнаружилось несовпадение параметров. Запрос с неизвестным результатом занимает место до сверки. При отказе панели, когда бан точно не выдан, место освобождается. После трёх выданных автобанов отправка прекращается и при перезапуске. Если сервис лимита недоступен, новые баны ждут восстановления связи. Сбор данных и проверка правил продолжаются.

В `rustapp_requests` сохраняются ID и время каждой попытки HTTP-запроса или открытия соединения WebSocket с RustApp. Повторы и неудачные обращения учитываются. Посмотреть число за последний час можно запросом:

```sql
SELECT count(*) FROM rustapp_requests
WHERE requested_at >= now() - interval '1 hour';
```

## Правила

Модули находятся в `app/services/moderation/patterns/`. P01 фиксирует совпадение регистрации Steam с ранее забаненным аккаунтом в пределах ±60 секунд. P02 может выдать бан при таком совпадении, если исходный бан предшествовал появлению новичка максимум на час. Для отправки по этой связке у обоих правил должно быть действие `ban`.

| Код | Независимое основание |
|---|---|
| P03 | Закрытый профиль без даты Steam и 3 разные жертвы за первые 10 минут первой игровой сессии новичка |
| P04 | Такой профиль и вход в течение 15 минут после бана другого пиратского аккаунта на сервере |
| P05 | 3 разные жертвы убиты в голову с 50 м за 30 минут |
| P06 | 3 разные жертвы убиты в голову за 30 минут, в логе каждой минимум 2 попадания стрелка с уроном по ней, все в голову |
| P07 | Минимум 5 убийств с 20 м за 30 минут, минимум 80% в голову и подтверждённая полнота окна |
| P09 | 3 разные жертвы за 30 минут в первый час после создания профиля на проекте |

Для P05–P07 учитываются винтовки, ПП и пулемёты по списку из исследования. Конфигурация правил передаётся JSON в `APP_MODERATION_PATTERNS`. Пример изменения двух правил:

```json
{"P05":{"meters":70,"version":2,"action":"ban"},"P04":{"action":"review"}}
```

Допустимые действия: `off`, `observe`, `review`, `ban`. Значения неуказанных порогов берутся из настроек соответствующего правила.

## Как разобрать бан

В комментарии RustApp сохраняются ID решения, код основного паттерна и краткое описание. Для просмотра полного основания решения №42:

```sh
docker compose --profile tools run --rm moderation python -m app.workers.show_decision 42
```

В `moderation_decisions` хранится одно решение на сессию. В нём видны версия и настройки каждого сработавшего паттерна, исходные ID банов или убийств, фактические показатели и время. Если одновременно подходят несколько оснований для бана, приоритет имеют P02, P06, P05, P03, P07, P04, P09 в указанном порядке. P01 отдельно сохраняет совпадение.

На вкладке «Решения» код правила открывает карточку с доказательствами. Вердикт и комментарий модератора сохраняются в локальной базе и служат для оценки правила. Статус бана управляется отдельно через RustApp.

Журнал обработчика можно смотреть командой `docker compose logs -f moderation`. В режиме наблюдения строка содержит предлагаемую причину; при включённой отправке журнал показывает отправку, затем подтверждение панели с номером бана. В обеих строках видны SteamID, код правила и фактическое основание.

Состояние `recorded` означает локальную запись, `pending` — очередь на отправку, `sending` — отправка началась и ещё не подтверждена в списке банов. После обнаружения комментария с идентификатором решения сохраняются `confirmed` и ID бана RustApp. При потерянном ответе обработчик ищет этот комментарий. Если результат остаётся неизвестным, запись остаётся в `sending` для сверки модератором. Действующий бессрочный бан всего проекта с блокировкой того же IP даёт состояние `superseded`. Несовпадение параметров выданного бана при сверке или окончательный отказ панели дают `failed`, изменение условий перед отправкой — `cancelled`.
